# Правила работы с проектом

## Работа с задачами

- Отвечать по-русски, кратко. Перед изменениями давать короткий план, после — изменённые файлы и результаты проверок. Не повторять известный контекст и вывод команд.
- Читать относящиеся к задаче файлы; искать через `rg` и `rg --files`. Независимые read-only проверки выполнять параллельно, ограничивать вывод.
- Интернет использовать для проверки изменчивых фактов и официальной документации, когда это необходимо. Подагентов не создавать без явного запроса.
- Сохранять пользовательские незакоммиченные изменения. Не выполнять `git push`, merge, rebase, удаление файлов или сброс изменений без запроса пользователя.
- Версию приложения пользователь меняет самостоятельно; не повышать её автоматически. Не добавлять Build ID и отдельные файлы версии. Развёртывание и управление VPS не выполнять без отдельного запроса.
- Новые файлы сразу добавлять через `git add <точный путь>`, без широких команд вроде `git add .`.
- После каждого создания или изменения файла побайтово проверять EOF и удалять завершающие `CR`/`LF`: последний байт должен быть содержательным.
- После изменений выполнять минимальную релевантную проверку. При изменении Gradle или модулей проверять `installDist`, упаковки — также `distZip`. Для правок только правил достаточно проверки текста и EOF.
- Тесты и тестовые библиотеки не добавлять, тесты не запускать без отдельной команды пользователя. Не выдавать компиляцию или `--dry-run` за проверку работы HTTP API.
- Не публиковать секреты, пароли, cookies, профили браузера и сгенерированные HTML-страницы. Секреты не записывать в отслеживаемые конфигурации.

## Код и модули

- Использовать Kotlin Code Style и существующие паттерны. Каждый именованный тип — в отдельном файле в `src/main/kotlin`.
- При рефакторинге сохранять публичный API. Менять его, добавлять зависимости и выполнять широкие рефакторинги только при необходимости для задачи, с объяснением.
- Писать код с небольшими контрактами и инъекцией зависимостей. Разделять HTTP DTO, предметные модели и модели хранения, преобразовывать явными мапперами.
- `app` — запуск Ktor, HTTP API, конфигурация окружения, связывание реализаций и завершение ресурсов. Различия профилей `local` и `vps` сосредоточены здесь; логика приложения общая.
- `feature:ozon` — логика Ozon и реализация `ProductPriceSource`.
- `core:products` — общие предметные модели и контракты без Ktor и Playwright.
- `core:browser` — Chrome, CDP и Playwright без знаний о конкретных маркетплейсах.
- Зависимости: `app` → `feature`/`core`, `feature` → необходимые `core`. Не создавать зависимости между фичами и из `core` в фичи.
- Самостоятельные фичи выделять в модули по мере реализации, без пустых модулей заранее. Общий код выделять при реальной потребности; контракты репозиториев оставлять в предметных модулях, реализации связывать в `app`.
- Общие настройки Kotlin/JVM 21 — в convention plugin из `build-logic`, версии зависимостей — в каталогах Gradle. Использовать `alias(...)` для доступных плагинов и `projects.*` для зависимостей модулей; сохранять `TYPESAFE_PROJECT_ACCESSORS`.
