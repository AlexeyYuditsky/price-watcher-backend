# price-watcher-backend

Backend для отслеживания цен товаров на маркетплейсах. Kotlin/JVM, Ktor, PostgreSQL, управление браузером для получения цен, многомодульный Gradle.

## Работа с задачами

- Отвечать по-русски, кратко. Перед изменениями — короткий план; после — изменённые файлы и результаты проверок. Не повторять известный контекст и вывод команд.
- Интернет использовать для проверки изменчивых фактов и официальной документации, когда это необходимо. Подагентов не создавать без явного запроса.
- Сохранять пользовательские незакоммиченные изменения. Не выполнять `git push`, merge, rebase, удаление файлов или сброс изменений без запроса пользователя.
- Перед новой реализацией изучить, как аналогичная задача уже решена в проекте, и следовать этому образцу, если он не противоречит этим правилам. При конфликте правила важнее; спорный случай уточнять у пользователя.
- Версию приложения пользователь меняет сам; не повышать её автоматически. Не добавлять Build ID и отдельные файлы версии.
- Развёртывание и управление сервером не выполнять без отдельного запроса.
- Не публиковать секреты, пароли, cookies, профили браузера и сгенерированные HTML-страницы. Секреты не записывать в отслеживаемые конфигурации.

## Файлы и форматирование

- Использовать Kotlin Code Style и существующие паттерны. Каждый именованный тип — в отдельном файле в `src/main/kotlin`.
- Новые файлы сразу добавлять через `git add <точный путь>`, без широких команд вроде `git add .`.
- После каждого создания или изменения файла побайтово проверять EOF и удалять завершающие `CR`/`LF`: последний байт должен быть содержательным.

## Код и модули

- При рефакторинге сохранять публичный API. Менять его, добавлять зависимости и выполнять широкие рефакторинги только при необходимости для задачи, с объяснением.
- Писать код с небольшими контрактами и инъекцией зависимостей. Разделять HTTP DTO, предметные модели и модели хранения, преобразовывать явными мапперами.
- `app` — точка входа: запуск Ktor, HTTP API (routing, DTO, мапперы запросов/ответов), конфигурация окружения, связывание реализаций, фоновые задачи и завершение ресурсов. Профиль окружения выбирается здесь; реализации под разные окружения могут жить в core-модулях, логика приложения общая.
- `feature:<name>` — самостоятельная предметная функциональность: сервисы, репозитории и их реализации, интеграции с конкретными маркетплейсами.
- `core:<name>` — переиспользуемая инфраструктура и общие предметные контракты: БД, браузер, общие модели. Core-модули не знают о конкретных фичах и маркетплейсах и не зависят от Ktor без необходимости.
- Зависимости: `app` → `feature`/`core`, `feature` → необходимые `core`. Не создавать зависимости между фичами и из `core` в фичи.
- Самостоятельные фичи выделять в модули по мере реализации, без пустых модулей заранее. Общий код выделять при реальной потребности; контракты репозиториев оставлять в предметных модулях, реализации связывать в `app`.
- Новый модуль подключать ко всем агрегирующим задачам корневого `build.gradle.kts`.
- Общие настройки Kotlin/JVM — в convention plugin из `build-logic`, версии зависимостей — в каталогах Gradle. Использовать `alias(...)` для доступных плагинов и типобезопасные accessors `projects.*` для зависимостей модулей.

## HTTP API

- Входные данные проверять на границе API до передачи в предметную логику.
- Ошибки возвращать в едином формате с осмысленными статус-кодами; не отдавать клиенту stack trace, внутренние сообщения и детали инфраструктуры.
- HTTP-контракт должен оставаться обратно совместимым с мобильным клиентом. Ломающие изменения — только с объяснением и согласием пользователя.

## Безопасность

- Пароли хранить только как стойкий хеш с солью; токены сессий — как хеши, с ограниченным сроком жизни и возможностью отзыва.
- Чувствительные эндпоинты (вход, регистрация, обновление токенов, тяжёлые операции) защищать ограничением частоты запросов.
- Не логировать пароли, токены, cookies и персональные данные.

## Конфигурация

- Секреты передаются через окружение или неотслеживаемые файлы, не через код и отслеживаемые конфиги.
- Конфигурацию проверять при старте: при отсутствующем или некорректном значении приложение сразу завершается с понятным сообщением.

## Ошибки, ресурсы и асинхронность

- Ожидаемые ошибки (некорректный ввод, недоступность источника цены, конфликт данных) выражать явными результатами или типизированными ошибками, а не непредусмотренными исключениями. `CancellationException` всегда пробрасывать.
- Браузер, соединения с БД и фоновые задачи ограничивать по параллельности, закрывать при завершении и при ошибке.
- Блокирующие операции не выполнять на потоках обработки запросов. Без GlobalScope и бесконтрольных scope.

## База данных

- Схему менять только новой версионной миграцией в каталоге миграций модуля БД. Уже существующие миграции не редактировать.
- Миграции применять к БД только по запросу пользователя.
- Операции из нескольких связанных изменений выполнять в одной транзакции. Время хранить в UTC.

## Проверки

- После изменений выполнять минимальную релевантную проверку. При изменении Gradle или модулей — сборку дистрибутива, при изменении упаковки — также архива дистрибутива. Для правок только правил достаточно проверки текста и EOF.
- Тесты и тестовые библиотеки не добавлять, тесты не запускать без отдельной команды пользователя. Не выдавать компиляцию или `--dry-run` за проверку работы HTTP API: её подтверждает только локальный запуск и запрос к эндпоинту, по согласию пользователя.
